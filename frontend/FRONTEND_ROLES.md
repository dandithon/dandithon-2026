# Frontend 역할 분담 — 조웅 · 강보성

## 1. 기준과 목표

- 현재 `main`의 시장 데모를 공통 기반으로 사용한다. 기존 개인 작업은 필요한 기능만 검토하여 옮기고, 친구의 구현을 통째로 덮어쓰지 않는다.
- React + JavaScript + Vite + Tailwind CSS를 유지한다.
- 요구사항은 [PRD](../docs/PRD.md), API 계약은 [API 명세](../docs/API.md), 협업은 [CONTRIBUTING](../CONTRIBUTING.md)을 따른다.
- 화면 제작뿐 아니라 담당 기능의 API 연동, UI 개선, 오류 처리, 테스트까지 각 담당자가 책임진다.
- 조웅은 **탐험·캐릭터·프로필과 프론트엔드 배포**, 강보성은 **가게·구매·리뷰·퀘스트와 공통 API 기반**을 맡는다. 서로의 PR과 통합 흐름은 교차 검수한다.

## 2. 역할 분담 당시 출발점

| 영역 | 현재 상태 | 남은 작업 |
|---|---|---|
| 시작·시장 | 기본 화면, 방향 버튼 이동, 충돌 처리 | 모바일 조작, 카메라, GPS, 전체 지도, 혼잡도 |
| 가게·메뉴·구매 | 가게별 메뉴, 즐겨찾기, 장바구니, 가상 구매 | 실제 API 연결, UI 보완, 구매 완료 화면 |
| 영수증·리뷰 | 로컬 주문 상태 변경, 리뷰 저장 | 서버 상태 연동, 내 리뷰 연결, 오류 처리 |
| 퀘스트 | 일부 일일 미션과 로컬 보상 | 서버 진행도·보상, 업적·이벤트의 확정 범위 반영 |
| 프로필·성장 | 전용 기능 미구현 | 프로필 3개 탭, 구매 횟수, 장비, 배지, 레벨·경험치 |
| 데이터·배포 | localStorage 기반 Mock API | API 계약 확정, 서버 연동, 배포 환경 및 검증 |

현재 가게 진입은 가상 방문 기록이며, 조이스틱 OFF는 GPS 이동이 아니다. 사진 미션은 완료 상태를 보여주는 샘플이다. 이 상태들을 실제 기능 완료로 간주하지 않는다.

## 3. 조웅 담당

상태는 현재 로컬 작업 기준이다. **완료**는 해당 기능의 로컬 구현·검증 완료, **부분 완료**는 구현된 범위와 남은 조건이 함께 있는 상태다. 실제 서버 연동·공개 배포·실기기 검수 완료를 의미하지 않는다.

| 작업 | 상태 | 완료한 내용 | 남은 작업 |
|---|---|---|---|
| 시작 화면·앱 진입 | ✅ 로컬 구현 완료 | 기존 시작 화면 유지, 초기 로딩·실패·재시도, 프로필 설정 오류 복구, 시작→시장 전환 | 실제 API 초기 로딩·인증 정책 연동 |
| 시장 탐험·캐릭터 | ✅ 로컬 구현 완료 | 연속 이동·충돌·방향별 이미지, 드래그 조이스틱·중앙 손잡이, 입력 해제·팝업 시 정지, 가게 복귀 위치 유지 | 실제 휴대폰 터치감·성능 검수 |
| 카메라·지도 조작 | ✅ 로컬 구현 완료 | 두 손가락 확대·축소, 맵 드래그, 이동 시 추적 복귀, 지도 경계 제한, 고정 UI와 지도 분리 | 실제 휴대폰 멀티터치 검수 |
| GPS 모드 | ◐ 부분 완료 | 권한 요청·위치 수신·오차 표시, 거부·시간 초과·재시도, 감시 정리, 좌표 변환 함수와 검증 | 실측 기준점·허용 오차 확정, 실제 맵 이동·방문 검증 연동 |
| 전체 지도·가게 진입 | ◐ 부분 완료 | Figma 전체 지도, 가게 목록, 공통 가게 ID로 상세 화면 연결 | 실제 가게 위치 데이터와 지도상의 위치 표시 |
| 대기시간·혼잡도 | ◐ Mock 구현 완료 | 시연 대기시간, 서문분식 NPC 대기줄, 단계별 표현, 정보 없음 처리, 가게별 목록 표시 | 실제 예측 API·갱신 주기·최종 혼잡도 규칙, 다른 가게 NPC 표현 |
| 프로필 | ◐ Mock 구현 완료 | 가방·내 리뷰·수집 음식 탭, 닉네임 변경·저장, 구매·리뷰 결과 반영 | 실제 사용자 API, 레벨·경험치 규칙 및 표시, 미제공 상세 디자인 검수 |
| 장비·배지 | ◐ 부분 완료 | 구매 횟수, 획득·잠금·착용·해제·저장, 미획득 착용 차단, 배지 3·5·10회와 다음 조건, 전체 장비 세트 정면 외형 | 서버 지급·착용 API, 최종 장비 조건, 개별 조합·목도리·측면·후면 외형 에셋 |
| 공통 모바일 UI | ◐ 구현 완료·실기기 검수 대기 | 너비·높이 비례 대응, 안전 영역, 공통 테마 재사용, 팝업 입력 차단, 브라우저 모바일 크기 검증 | 실제 휴대폰 화면·터치·키보드 검수 |
| 프론트엔드 배포 | ◐ 준비 완료·공개 배포 대기 | 환경 변수 예시, 에셋 검사·테스트·빌드 명령, 정적 빌드, 로컬 프로덕션 미리보기, 배포·복구 절차 문서 | 호스팅·계정·도메인 선정, HTTPS 공개 배포, 배포 URL에서 API·위치 권한 검증 |

## 4. 강보성 담당

| 작업 | 구현·개선 범위 | 완료 기준 |
|---|---|---|
| 가게 상세 | 소개·메뉴 진입·즐겨찾기·영업 정보·공유, 가게별 정보 연동 | 가게 간 메뉴·리뷰가 섞이지 않고 미등록 정보가 구분됨 |
| 메뉴·장바구니 | 목록·상세·수량·합계·삭제, 임시 이미지 및 UI 개선 | 수량·가격이 일관되고 직접 구매와 장바구니 구매의 처리 정책이 명확함 |
| 가상 구매 | 주문 API, 잔액 부족·실패·중복 요청 처리, 구매 완료 화면 | 서버 성공 결과로 코인·주문·구매 횟수를 갱신하며 실패를 성공으로 표시하지 않음 |
| 영수증 | 주문 목록·상태 조회, 상태 갱신, 리뷰 진입 | 조리 중/완료/리뷰 완료 상태가 맞고 화면을 벗어나면 불필요한 조회가 정리됨 |
| 리뷰 | 리뷰 목록·작성·별점·검증, 서버 등록, 프로필 연동용 데이터 제공 | 작성 가능 주문만 제출하며 등록 결과가 가게·영수증·내 리뷰에 반영됨 |
| 퀘스트 | 일일 미션·업적·이벤트, 진행도와 보상 수령 API | 서버의 수령 가능 여부를 따르며 중복 보상 없이 코인·경험치를 갱신함 |
| 담당 화면 UI | 가게·메뉴·주문·영수증·리뷰·퀘스트의 Figma 반영 | 임시 폼·이모지·하드코딩 수치를 정리하고 로딩·빈 목록·오류를 표시함 |
| 공통 API 기반 | HTTP 요청 모듈, 공통 오류 처리, 환경별 API 주소, Mock/서버 전환 | UI가 저장 방식을 직접 다루지 않고 동일한 API 경계를 사용함 |
| 백엔드 연동 조율 | 필요한 데이터·상태값·오류 규격 취합, API 계약 변경 공유 | 조웅 담당 API를 포함해 계약 누락과 불일치를 추적함 |
| 자동 검증 기반 | 기존 테스트 유지·확장, 빌드·테스트 자동화 구성 | PR에서 기능에 맞는 검증을 실행하고 실패가 확인되도록 함 |

공통 API 조율을 맡는 것이 모든 API 연결을 대신 구현한다는 뜻은 아니다. 조웅 담당 화면의 API 호출과 상태 처리는 조웅이 구현한다. AI 리뷰 요약·사진 미션 등 미확정 기능은 기획 범위와 API를 확인한 뒤 진행한다.

## 5. DB 연동과 데이터 책임

프론트엔드는 **백엔드 API를 통해 DB 데이터를 조회·변경**한다. DB 스키마·접속·마이그레이션·서버 트랜잭션·서버 배포는 백엔드 담당 범위다. DB 비밀번호나 서버 전용 비밀키를 프론트엔드에 넣지 않는다.

| 데이터·계약 | FE 구현 담당 | 함께 정할 사항 |
|---|---|---|
| 사용자 식별·인증 방식 | 강보성: 공통 요청 처리 / 조웅: 초기 진입 처리 | 로그인 또는 시연 사용자 정책, 세션 유지·만료 처리. 미확정 인증 화면은 임의 추가하지 않음 |
| 시장·가게 위치·대기시간 | 조웅 | 지도 좌표, 가게 ID, 위치 검증 방식, 혼잡도 규칙 |
| 가게 상세·메뉴·즐겨찾기 | 강보성 | 가게·메뉴 ID, 가격 단위, 데이터 없는 경우 |
| 구매·코인·영수증 | 강보성 | 중복 요청 정책, 주문 상태 전환, 잔액·구매 횟수·보상 갱신 결과 |
| 리뷰·퀘스트 | 강보성 | 리뷰 작성 자격, 진행도, 수령 조건, 일일 미션 초기화 기준 |
| 프로필·장비·배지·구매 횟수 | 조웅 | 획득과 착용 구분, 보상 조건, 레벨·경험치 표현 |

`docs/API.md`의 엔드포인트와 인증 방식은 아직 미확정이므로 임의의 주소·응답 구조를 확정하지 않는다. 각자 필요한 계약을 정리하고 강보성이 취합해 백엔드와 조율한다. 계약 변경은 관련 담당자가 확인한 후 문서와 구현에 함께 반영한다.

### 화면 사이의 데이터 연결

| 행동 | 발생 화면 담당 | 다른 화면에 반영할 결과 |
|---|---|---|
| 구매 성공 | 강보성 | 조웅: 잔액·구매 횟수·장비·배지·프로필 갱신 / 강보성: 영수증·퀘스트 갱신 |
| 리뷰 등록 | 강보성 | 조웅: 내 리뷰 갱신 / 강보성: 가게 리뷰·주문 상태·퀘스트 갱신 |
| 퀘스트 보상 수령 | 강보성 | 조웅: 표시 코인·경험치·레벨 갱신 / 강보성: 수령 상태 갱신 |
| 장비 착용·해제 | 조웅 | 프로필과 시장 캐릭터 외형을 같은 상태로 갱신 |
| 실제 방문 검증 결과 수신 | 조웅 | 강보성: 서버 기준 방문 퀘스트 진행도 갱신 |

서버가 확정한 결과 또는 재조회 결과를 공통 상태에 반영한다. 화면마다 코인·리뷰·보상을 별도로 누적하지 않는다. Mock의 localStorage 데이터를 서버 데이터와 자동 합산하지 않는다.

| `src/pages/StorePage.jsx`, `MenuPage.jsx`, `StoreScene.jsx` 등 가게 UI | 강보성 | 지도 위치 데이터와 가게 상세 데이터의 ID를 일치시킴 |
| `OrderDialog.jsx`, `ReceiptDialog.jsx`, `QuestDialog.jsx`, `ExtraDialogs.jsx` | 강보성 | 공통 다이얼로그의 인터페이스 변경은 조웅과 확인 |
| `src/App.jsx` | 조웅: 통합 책임 | 강보성이 필요한 상태·콜백을 공유하고 같은 부분의 동시 수정을 피함 |
| `src/api/market.js`, `src/mocks/fixtures.js`, 신규 공통 API 모듈 | 강보성: 구조 관리 | 조웅의 기능 API 추가는 계약과 수정 범위를 먼저 공유. 필요하면 기능별 파일로 분리 |
| `src/styles/global.css`, `Dialog.jsx`, `Art.jsx` 등 공통 UI | 조웅: 기준 관리 | 강보성은 담당 화면의 로컬 스타일을 수정하고 공통 변경은 영향 화면까지 확인 |
| `src/assets/figma.json`, `public/assets/` | 각 화면 담당자 | 기존 키·공유 에셋을 덮어쓰거나 삭제하기 전 사용처 확인 |
| `package.json`, lockfile, `vite.config.js` | 조웅: 설정 통합 | 강보성의 테스트·API 설정 변경과 중복 작업을 조율 |
| `tests/` | 각 기능 담당자 | 강보성은 공통 실행·자동화, 조웅은 탐험·프로필 검증을 담당 |

자동화 파일을 `.github/`에 추가해야 하는 경우 해당 영역 담당자와 변경 범위를 조율한다. 백엔드 파일은 직접 수정하지 않고 필요한 변경을 요청한다.

## 7. 진행 순서

1. **공통 계약 정리 — 강보성 주도, 조웅 참여:** 가게·메뉴·사용자 ID, 상태값, API 요구사항, Mock 전환 방식을 정리한다. 미확정 기획과 디자인을 분리해 기록한다.
2. **공통 상태 경계 정리 — 조웅 주도, 강보성 참여:** `App.jsx`의 화면·사용자 상태 연결을 정리하고 시장 복귀 시 위치 유지, 구매 이후 갱신 경로를 정한다.
3. **담당 기능 병행 개발 — 각 담당자:** 조웅은 탐험→지도·혼잡도→프로필·장비·배지, 강보성은 가게→구매·영수증→리뷰·퀘스트를 연결한다. API가 준비되지 않은 부분은 명시적인 Mock으로 검증한다.
4. **실제 API 연결 — 각 담당자:** 강보성의 공통 요청 기반 위에서 담당 화면을 연결하고 실패·재시도·새로고침 후 데이터 유지까지 확인한다.
5. **모바일 UI·통합 검수 — 조웅은 탐험·전체 레이아웃, 강보성은 거래 흐름:** Figma와 비교하고 실기기에서 터치·스크롤·팝업·키보드를 확인한다.
6. **배포 및 배포 환경 검증 — 조웅 주도, 강보성 교차 검수:** 자동 검증을 통과한 코드로 배포하고 실제 URL에서 전체 사용자 흐름을 확인한다.

## 9. 작업 범위와 협업 원칙

- 기능 단위로 작업을 나누고 한 PR에는 하나의 주요 목적을 담는다. 커밋·PR 메시지는 변경점과 검증 내용을 간결하게 작성한다.
- 공통 파일을 바꾸기 전에 수정 구간을 공유하고, 상대 작업이 반영되면 최신 `main`을 기준으로 통합한다.
- 담당자는 구현뿐 아니라 해당 기능의 API 협의·UI 개선·테스트·문서화를 마무리한다. 상대 담당자는 리뷰와 통합 검증을 지원한다.
- 미확정 디자인은 디자이너에게 확인하고, 임시 UI를 최종 디자인으로 간주하지 않는다.
- 실제 PG 결제, 실제 음식 주문, 점주 관리, QR 방문 인증, AI 추천 기능은 현재 분담에 포함하지 않는다.
- 배포 완료와 서비스 기능 완료를 구분한다. 배포 후에도 남아 있는 Mock·미연동·미검증 항목을 README에 표시한다.
