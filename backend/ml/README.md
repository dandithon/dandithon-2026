# 서문분식 합성 데이터 기반 준비시간 모델

## 무엇을 만들었나
실제 프로젝트 메뉴 네 가지(`tteok` 떡볶이, `sundae` 순대, `fried` 튀김 세트, `fish` 오뎅)의 수량을 입력받아 **해당 주문 자체의 준비시간**을 예측한다. Spring은 DB의 앞선 주문이 끝날 때까지 남은 시간에 이 값을 더해 새 주문의 완료 시각을 저장한다.

- 원천: 자체 조리 시뮬레이터. **실제 서문시장 관측 데이터도, GPT가 생성한 시간값도 아니다.**
- 100개 가상 날짜 × 50건 = 5,000건. 데이터: `datasets/seomun-synthetic.csv`.
- 80일 4,000건 학습 / 별도 20일 1,000건 평가. 같은 날짜가 양쪽에 들어가지 않는다.
- RandomForestRegressor 64개 트리, 최대 깊이 12, 잎 최소 표본 2, seed 42.
- 메뉴당 0~99개(0은 미주문), 최소 한 메뉴. 보통 주문 1~5개와 드문 대량 주문 6~99개를 섞어 기존 API 수량 범위를 다룬다. 실제 주문 분포를 나타내지는 않는다.
- 주문 수량만 모델의 입력이다. 배달거리·비·개인정보·실제 매장 혼잡도는 사용하지 않는다.

## 합성 데이터의 조리 가정
| 메뉴 | 한 배치 준비시간 | 한 번에 처리하는 수량 |
|---|---:|---:|
| 떡볶이 | 2분 | 4인분 |
| 순대 | 2.5분 | 3인분 |
| 튀김 세트 | 4분 | 2세트 |
| 오뎅 | 1분 | 5개 |

이 숫자는 현장 측정값이 아닌 **시연용 가정**이다. 한 주문 안에서는 메뉴를 동시에 준비하며 가장 늦게 끝나는 메뉴를 기준으로 한다. 주문 간에는 접수 순서대로 한 주문씩 처리하는 단순 FIFO 가정이다. 날짜별 속도 0.85~1.15배와 표준편차 0.25분의 잡음을 넣었다. 주문 간격은 가상 날짜별로 평균 2분/6분의 지수분포다. 실제 분식집의 조리 설비·미리 조리한 재고·병렬 작업을 검증한 것이 아니다.

CSV의 `queue_minutes`는 앞선 주문의 완료까지 남은 가상 시간, `prep_minutes`는 해당 주문 준비시간, `eta_minutes`는 두 값의 합이다. 학습 정답은 `prep_minutes`이며 완료 이후 정보나 정답을 입력 피처로 사용하지 않는다.

## 재현하기
Python 3.9 이상에서, `backend/` 기준:

```sh
python3 -m venv ml/.venv
ml/.venv/bin/pip install -r ml/requirements.txt
ml/.venv/bin/python ml/train_eta.py
```

생성물:
- `ml/datasets/seomun-synthetic.csv`: 합성 주문 5,000건, 저장소 포함.
- `ml/metrics.json`: 별도 날짜 평가 결과·데이터 SHA-256·학습 버전, 저장소 포함.
- `ml/artifacts/market_eta_model.pkl`: Python용 학습 모델. 로컬 생성물이며 커밋하지 않는다.
- `src/main/resources/eta/seomun-model.json`: 학습된 트리의 분기/출력값. Spring JAR에 포함하므로 운영 서버에 Python/FastAPI 추가 설치가 필요 없다.
- `src/main/resources/eta/parity-vectors.json`: Python 결과와 Java 추론을 비교하는 24개 고정 입력.

내보낸 JSON은 새로운 계산식이나 학습되지 않은 대체 모델이 아니다. sklearn이 학습한 각 트리를 같은 조건으로 순회해 평균낸다. 내보내기 시 평가 1,000건의 예측값 일치를 확인하고, Java 통합 테스트가 고정 입력에 대해 1e-9 이내 일치를 검증한다. 외부 출처의 pickle 파일을 서버에서 불러오지 않는다.

## 평가와 한계
`metrics.json`의 MAE는 **합성 환경의 분 단위 평균 절대 오차**이고 R²는 정확도 백분율이 아니다. 학습 데이터 준비시간의 평균만 답하는 기준선과 비교한다. 대기열 잔여시간은 알고 있다고 가정하므로 준비시간 MAE와 총 ETA MAE가 같다. 실제로는 앞선 주문의 예측 오차가 누적될 수 있으며 이 평가는 그 오차까지 검증하지 않는다.

현재 준비시간 MAE 약 1.26분, 평균 기준선 약 17.37분. 큰 수량의 주문이 포함된 이 합성 분포에서의 수치다. 상수 대신 원래 조리 공식을 직접 계산하는 방식이 더 적합할 수도 있으며, 이 모델이 원래 시뮬레이터보다 낫다는 주장은 하지 않는다. 임의 공식의 패턴을 학습한 시제품이지 실제 시장에서 AI 효과가 입증된 서비스가 아니다.

발표 시 권장 설명: “서문분식 네 메뉴를 대상으로 자체 조리 시뮬레이터에서 생성한 5,000건을 사용했습니다. 학습 모델이 실제 게임 주문과 연결되어 준비시간을 예측하며, 실제 매장 정확도는 현장 데이터로 추가 검증해야 합니다.”

## 운영 연결
- 기본 `SEOMUN_ETA_ENABLED=false`: 기존 주문은 15초 완료, 가게 목록은 기존 고정 대기시간 유지. 새 견적 API는 시험 가능하고 `appliedToOrders=false`를 반환한다.
- 프론트 연결 후 `SEOMUN_ETA_ENABLED=true`로 서문분식 주문·가게 목록에 적용. 다른 가게는 기존 동작 유지.
- `SEOMUN_ETA_SECONDS_PER_MINUTE=5`: 가상 1분을 실제 5초에 진행. 12분 견적이면 실제 약 60초 후 완료. 60으로 설정하면 1분당 실제 60초다. 허용 범위 1~60.
- 진행 중인 주문의 시각은 DB에 고정된다. 배속/모델을 바꾸어도 이전 주문의 완료 시각을 다시 예측하지 않는다. 남은 주문이 없는 상태에서 설정을 바꾸는 것을 권장한다.
- `readyAfterSeconds`는 최초 주문 시각부터 완료까지의 실제 초이며, 재시도 시 같은 주문의 값이다. 재조회 영수증의 서버 상태를 기준으로 리뷰 가능 여부를 결정한다.
- V5 마이그레이션: 기존 주문 완료 시각을 `ordered_at+15초`로 채우고 기존 기록/잔액/리뷰를 유지한다. 시연 초기화로 주문을 삭제하면 대기열도 함께 비워진다.
- 공용 게스트 userId 1 정책은 유지된다. 여러 접속자의 주문은 같은 잔액/진행도를 공유한다. 사용자 분리나 실제 음식 주문 기능을 새로 추가하지 않는다.
