# 프론트엔드 구현 프로세스 및 역할 분담

## 1. 목적과 기준

프론트엔드 2명이 서로의 작업을 기다리는 시간을 줄이고, 시장 탐험부터 구매·리뷰·보상까지 연결된 MVP를 구현하기 위한 작업 계획이다.

- **FE A: 본인** — 시장 탐험, 캐릭터, 프로필·장비 및 앱 기반 담당
- **FE B: 다른 프론트엔드 팀원** — 가게·구매, 영수증·리뷰, 퀘스트 및 공통 UI·API 통신 기반 담당
- 위 분담은 화면 수보다 구현 난도와 기능 간 연결을 기준으로 한다. A는 좌표·이동·렌더링을, B는 구매·활동의 데이터 흐름을 중심으로 맡는다.
- 요구사항은 [PRD](../docs/PRD.md), 협업은 [CONTRIBUTING](../CONTRIBUTING.md), 작업 범위는 [AGENTS](../AGENTS.md)를 따른다.
- 화면 기준은 [Figma 디자인](https://www.figma.com/design/PN8yd5L6JGengjjhdmahUB/?node-id=0-1)이다. 디자인에만 있는 기능은 구현 확정으로 간주하지 않는다.
- 프론트엔드는 React + JavaScript + Vite 기반 모바일 웹으로 진행한다. 초기 탐험 기반은 React 상태와 SVG로 구성하며, 최종 게임 에셋·렌더링 고도화·API 계약은 추가 협의한다. 현재 구현 및 미구현 범위는 [실행 안내](README.md)를 참고한다.

|---|---|---|

| 공통 API 통신 기반 | B | API 클라이언트, 합의한 인증 정보 전달, 공통 오류 처리, Mock 전환 방식. 개별 기능 API 연동은 각 담당자가 수행 |
| 공통 상태·화면 연결 기반 | A | 사용자 상태를 공유하는 구조, 현재 열린 패널 관리, 패널 열기·닫기와 이동 입력 제어, 기능 간 갱신 연결 |

| 시장 탐험 | A | 2D 맵, 캐릭터 렌더링, GPS 좌표 변환, 조이스틱, 모드 전환, 확대·축소, 이동 가능 영역 처리 |
| 탐험 화면 UI·전체 지도 | A | 프로필·코인 표시, 지도·퀘스트·영수증 진입 버튼, 전체 지도, 현재 위치·가게 위치 연결 |
| NPC 및 혼잡도 | A | 가게 선택 판정, NPC 배치, 대기시간 조회·표시, 혼잡도별 NPC 대기줄, 데이터 없음·Mock 표시 |

| 가상 코인 구매 | B | 수량·총액 표시, 구매 요청, 중복 제출 방지, 잔액 부족·실패 처리, 구매 완료 UI |
| 영수증 | B | 주문 목록, 조리 중·조리 완료·리뷰 완료 표시, 리뷰 작성 진입 조건 |
| 리뷰 | B | 가게 리뷰 목록, 리뷰 입력·검증·등록, 주문 연결, 프로필의 내 리뷰 탭 콘텐츠 |
| 프로필·장비·음식 배지 | A | 프로필 기본 정보, 탭 컨테이너, 가방·잠금·착용 UI, 캐릭터 외형 반영, 수집 음식·배지·진행도 |
| 퀘스트 | B | 일일 미션·업적·이벤트 목록, 진행률, 완료 조건 표시, 보상 수령·중복 제출 방지 |
| 기능별 검증 | 각 담당자 | 본인 기능의 정상·실패·빈 상태와 API 연동 검증 |
| 통합·배포 검증 | A 주도, B 참여 | 전체 사용자 흐름, 실제 대상 기기, 빌드·배포 설정 확인. B는 구매·리뷰·보상 데이터 일관성 집중 검증 |

### 경계가 겹치는 기능의 담당 원칙

- **프로필:** A가 프로필 레이아웃과 탭을 소유한다. B는 내 리뷰 콘텐츠를 독립된 컴포넌트로 제공한다. B가 프로필 전체 파일을 직접 수정하지 않는다.
- **가게 진입:** A는 선택한 가게 식별자를 전달하고, B는 해당 가게의 상세 패널을 연다. 가게 이름이나 화면 좌표로 상품 데이터를 연결하지 않는다.
- **코인:** A는 탐험 화면의 코인을 표시하고, B는 구매·보상 요청을 처리한다. 양쪽 화면은 동일한 사용자 데이터를 참조한다.
- **장비:** A가 프로필의 착용 상태와 탐험 캐릭터 외형을 함께 관리한다. B의 구매 성공 후에는 관련 장비·배지 데이터를 갱신하도록 연결한다.
- **공통 코드:** 프로젝트 설정·화면 연결·공통 상태는 A, 공통 UI·API 클라이언트는 B가 수정 책임을 갖는다. 계약을 바꾸는 경우 상대방과 먼저 합의한다.

## 3. 구현 프로세스

### 단계 1. 구현 기준과 인터페이스 합의

두 사람이 함께 다음 항목을 정하고, 해당 결정이 필요한 작업부터 시작한다.

1. 모바일 웹 또는 앱 등 실행 대상, 지원 화면 크기, 개발·빌드·배포 방식 결정
2. 지도 렌더링, 상태 관리, 화면 전환, API 호출 방식 결정
3. Figma의 구현 대상 버전과 화면별 동작 확인
4. 디자이너와 배경·캐릭터·NPC·음식·장비·UI 에셋의 전달 방식 확인
5. BE와 사용자·가게·상품·주문·리뷰·장비·배지·퀘스트 식별자 및 요청·응답 구조 합의
6. 화면 간 전달값, 공통 사용자 상태, 성공 후 갱신할 데이터 목록 합의

**완료 기준:** 두 사람이 동일한 화면 범위와 데이터 구조로 작업할 수 있고, 미확정 사항은 별도로 표시되어 있다. API 계약 확정 내용은 BE와 함께 `docs/API.md`에 반영하도록 협의한다.

### 단계 2. 공통 기반 구축

- **A:** 프로젝트와 앱 진입 구조를 생성하고, 시장 화면 위에 패널을 여닫는 구조 및 사용자 상태 공유 기반을 만든다.
- **B:** A의 최소 프로젝트 설정이 준비되면 공통 UI와 API 통신 기반을 구현한다. 그 전에는 디자인 값·공통 컴포넌트 목록과 API 계약을 정리한다.
- **공동:** 의존성·설정 파일은 동시에 수정하지 않고 담당자를 정해 변경한다. 각자 로컬에서 동일한 명령으로 실행되는지 확인한다.

**완료 기준:** 시작 화면에서 빈 시장 화면에 진입할 수 있고, 공통 패널·버튼과 합의한 형식의 Mock API를 양쪽에서 사용할 수 있다.

### 단계 3. Mock 기반 핵심 흐름 병렬 구현

| A 진행 순서 | B 진행 순서 |
|---|---|
| 맵·캐릭터 표시 → 조이스틱 이동 → 가게 선택 전달 | 가게 식별자를 받는 상세 화면 → 메뉴 조회 → 수량·구매 화면 |
| 탐험 화면 버튼 → 전체 지도 → 패널 연결 | 구매 결과 → 영수증 → 리뷰 입력·등록 |
| GPS 연결·좌표 변환 → 이동 모드 전환 | 공통 구매·주문·리뷰 데이터의 상태 전환 검증 |

- B는 임시 가게 선택 진입점을 이용해 A의 맵 완성을 기다리지 않고 작업한다.
- A는 합의된 가게·사용자 Mock 데이터로 B의 화면 완성을 기다리지 않고 이동을 구현한다.
- 임시 진입점은 개발용으로 구분하고, 통합 시 실제 진입 경로로 교체한다.
- Mock 데이터는 공통 계약을 따르고, 화면별로 서로 다른 코인 잔액이나 주문 목록을 따로 만들지 않는다.

**완료 기준:** 시장에서 가게를 열고, 가상 구매 후 영수증을 확인하며, 조리 완료된 주문에 리뷰를 작성하는 흐름이 Mock 환경에서 연결된다.

### 단계 4. 성장·활동·혼잡도 기능 확장

- **A:** 프로필, 가방·장비 착용, 외형 변경, 음식별 배지·진행도, 혼잡도별 NPC 표현을 구현한다.
- **B:** 내 리뷰 탭 콘텐츠와 퀘스트 목록·진행률·보상 수령을 구현한다.
- **공동:** 구매·리뷰·보상 수령 후 관련 화면이 함께 갱신되도록 연결한다. 패널을 닫아도 캐릭터 위치와 이동 모드가 유지되는지 확인한다.

**완료 기준:** 핵심 활동의 결과가 프로필·배지·퀘스트·코인에 일관되게 반영되고, 획득과 착용, 완료와 보상 수령 상태가 구분된다.

### 단계 5. 실제 API 연결

API가 준비된 기능부터 단계 3~4와 병행할 수 있다.

- 각 담당자는 본인 기능의 Mock 호출을 실제 API로 교체한다. B가 모든 기능의 API 연동을 대신하지 않는다.
- 로딩, 오류, 재시도, 빈 데이터, 중복 제출을 화면 상태로 처리한다.
- 구매·보상·리뷰의 성공 여부는 서버 결과를 기준으로 판단한다.
- 실제 데이터와 시연용 Mock 데이터를 구분한다. Mock 대기시간을 실제 AI 예측으로 표시하지 않는다.

**완료 기준:** 각 기능의 API 성공·실패가 UI에 올바르게 반영되고, 연관된 데이터가 갱신된다. 미연동 기능은 완료로 표시하지 않는다.

### 단계 6. 통합 검증 및 마무리

- **A 중심:** GPS 권한 거부·위치 미수신, 조이스틱 모드 전환, 확대·축소, 패널 입력 충돌, 장비 외형 및 모바일 화면 대응 확인
- **B 중심:** 코인 부족, 구매 연속 클릭·실패, 주문 상태별 리뷰 제한, 리뷰 중복 제출, 퀘스트 보상 중복 수령 확인
- **공동:** 시작 → 탐험 → 가게 → 구매 → 영수증 → 리뷰 → 보상 확인 → 장비 착용 → 재탐험 흐름 검증
- **공동:** 패널 열기·닫기, 뒤로 가기, 긴 목록 스크롤, 로딩·오류·빈 화면, 배포 환경에서의 API·위치 기능 확인

**완료 기준:** 전체 사용자 흐름을 대상 환경에서 재현할 수 있고, 남은 Mock·미구현·확인 필요 항목을 구분해 기록한다.

## 4. 두 담당자가 맞춰야 할 연결 계약

아래는 필요한 연결의 의미를 정리한 것이며, 실제 함수명·필드명·상태값은 합의 후 결정한다.

| 연결 지점 | 전달 또는 갱신 내용 | 책임 |
|---|---|---|
| 시장 → 가게 화면 | 선택한 가게 식별자 | A 전달, B 조회·표시 |
| 탐험 버튼 → 활동 패널 | 지도·프로필·영수증·퀘스트 중 열 대상 | A 공통 연결, 각 담당자 콘텐츠 제공 |
| 프로필 → 내 리뷰 | 현재 사용자의 리뷰 목록 콘텐츠 | B 제공, A 탭 연결 |
| 구매 성공 | 코인·주문·음식 구매 횟수·장비·배지·관련 퀘스트 갱신 | B 성공 통지, A 공통 갱신 연결, 각 기능 담당자 조회 반영 |
| 리뷰 등록 성공 | 주문의 리뷰 상태·가게 리뷰·내 리뷰·관련 퀘스트 갱신 | B |
| 퀘스트 보상 수령 | 퀘스트 수령 상태·코인·경험치·레벨 갱신 | B 성공 통지, A 사용자 표시 반영 |
| 장비 착용 성공 | 보유 장비·착용 상태·프로필 및 맵 캐릭터 외형 갱신 | A |
| 패널 열기·닫기 | 배경 이동 입력 차단·복원, 기존 위치 유지 | A 공통 처리, B 패널 연결 준수 |

서버가 관리하는 보상 조건이나 잔액 계산을 프론트엔드에서 별도 확정하지 않는다. 화면 갱신은 합의된 서버 응답 반영 또는 관련 데이터 재조회 방식으로 처리한다. Mock 단계에서도 같은 계약을 사용한다.

## 5. 구현 전 확인할 디자인·기획 항목

| 확인 항목 | 확인 내용 | 협의 주도 |
|---|---|---|
| 혼잡도 구간 | 디자인의 `10~15분`과 PRD 예시의 `10~20분` 차이, 누락된 구간 및 경계값, NPC 수 확정 | A → PM·디자이너·BE |
| 게임 에셋 | 분리된 배경·캐릭터·NPC·장비 제공 여부, 이동 방향·걷기 프레임, 장비 합성 방식, 맵 좌표·이동 영역 | A → 디자이너 |
| 위치 동작 | GPS와 맵 좌표 대응, 실내 위치 오차·층수, 권한 거부·시장 밖 위치 처리, 가상 이동과 방문 판정 구분 | A → PM·BE |
| 구매 흐름 | 즉시 주문과 메뉴 담기의 차이, 장바구니 포함 여부, 구매 완료 후 이동 위치, 가상 구매 표시 | B → PM·디자이너·BE |
| 추가 UI 기능 | AI 요약·찜·공유·닉네임 변경·코인 추가 버튼의 MVP 포함 여부와 동작 | 각 화면 담당자 → PM |
| 추가 화면·상태 | 리뷰 입력, 내 리뷰·수집 음식 탭, 잠금 해제·착용 상태, 로딩·실패·빈 목록 디자인 | 각 화면 담당자 → 디자이너 |
| 보상 규칙 | 장비 획득 조건, 음식별 구매 횟수 집계 기준, 퀘스트 초기화·보상 수령 방식 | A·B → PM·BE |
| 사용자 식별 | 로그인·게스트 여부 및 초기 사용자·코인 데이터 제공 방식 | B → PM·BE, A 진입 화면 반영 |

기획서상 배지는 음식별 구매 3회·5회·10회에 브론즈·실버·골드를 지급한다. 장비 조건은 예시와 실제 정책을 구분해 확정한다. 구현 범위를 새로 추가하거나 미확정 동작을 임의로 결정하지 않는다.

실제 PG 결제, 실제 음식 주문, QR 방문 인증, AI 코스·길 찾기 추천, 점주 주문 관리 기능은 현재 구현 범위에 포함하지 않는다.

## 6. 작업 및 리뷰 원칙

- 기능별 Issue와 작업 브랜치를 사용하고, PR을 통해 상대 담당자가 검토한다.
- 공통 기반을 작게 먼저 병합한 뒤 기능 단위로 통합한다. 전체 화면이 완성될 때까지 연결을 미루지 않는다.
- 기능별 코드는 담당 영역으로 분리하고, 공통 파일 변경은 소유 담당자와 먼저 조율한다. 구체적인 폴더명은 스택 확정 후 정한다.
- PR에는 구현 범위, UI 화면, 테스트 결과, Mock 사용 여부, 남은 확인 사항을 기록한다.
- FE A와 FE B 모두 본인 기능의 UI·API 연동·오류 처리·검증까지 책임진다.
- 다른 파트나 공통 문서의 변경이 필요하면 관련 담당자와 협의하고, 별도 요청 없이 직접 변경하지 않는다.
